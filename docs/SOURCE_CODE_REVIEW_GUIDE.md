# AutoQ-Guard 핵심 소스코드 리뷰 가이드

> 목적: 코드를 전부 암기하는 것이 아니라, **데이터가 들어와 결과가 나오기까지의 흐름과 중요한 설계 판단**을 설명하기 위한 자료입니다.

## 1. 먼저 외울 한 문장

AutoQ-Guard는 기업 원본 CSV를 표준 형식으로 바꾸고 오류를 검사한 뒤, 부품 LOT별 위험과 영향 VIN·예상 손익을 계산하여 데이터베이스와 대시보드로 제공하는 파이프라인입니다.

## 2. 전체 실행 흐름

```text
기업 원본 CSV
   ↓
enterprise_import.py
컬럼 매핑·값 변환
   ↓
enterprise_data_validator.py
형식·필수값·중복·참조관계 검사
   ↓
enterprise_risk_analyzer.py
LOT 위험점수·영향 VIN·예상 손익 계산
   ↓
enterprise_database.py
검증 결과를 DB에 안전하게 적재
   ↓
enterprise_dashboard.py
로그인·검색·대시보드·관리자 API 제공
```

이 전체 순서를 조정하는 파일이 `enterprise_pipeline.py`입니다.

## 3. 가장 중요한 파일 8개

### 3.1 `src/enterprise_pipeline.py` — 전체 공정 관리자

**역할**

- 데이터 반입 → 위험분석 → DB 구축 → 정상조회 시험을 순서대로 실행합니다.
- 앞 단계가 실패하면 뒤 단계를 실행하지 않습니다.
- 성공한 실행만 `current` 폴더에 발행합니다.
- 실패한 실행이 기존 정상 결과를 덮어쓰지 않도록 합니다.

**핵심 함수**

- `run_pipeline()`：모든 단계를 순서대로 실행하는 중심 함수
- `_write_summary()`：실행 결과를 JSON으로 기록

**핵심 코드 의미**

```python
if imported["status"] != "READY":
    raise RuntimeError("기업 원본 변환 또는 데이터 검증 실패")
```

데이터 검증을 통과하지 못하면 위험분석으로 넘어가지 않는 **품질 Gate**입니다.

```python
publish.rename(current)
```

정상 완료한 임시 결과만 현재 운영 결과로 교체합니다. 중간 실패 파일이 서비스에 노출되는 것을 막습니다.

**면접 답변**

> 파이프라인은 네 단계로 구성했고, 각 단계가 READY일 때만 다음 단계가 실행됩니다. 특히 실패 실행은 별도 실행 폴더에 남기고 기존 정상 `current`는 유지하도록 설계했습니다.

### 3.2 `src/enterprise_import.py` — 기업 데이터 번역기

**역할**

- 기업마다 다른 CSV 파일명과 컬럼명을 표준 컬럼으로 매핑합니다.
- 날짜, 대소문자, 백분율 같은 값을 표준 형식으로 변환합니다.
- 허용된 입력 폴더 밖의 파일을 읽지 않도록 경로를 검사합니다.

**핵심 함수**

- `safe_source_path()`：입력 경로 이탈 차단
- `apply_transform()`：값 형식 변환
- `convert_table()`：한 파일을 표준 테이블로 변환
- `import_and_validate()`：변환과 검증을 한 번에 실행

**면접 답변**

> 실제 기업 데이터는 컬럼명이 다르기 때문에 바로 분석할 수 없습니다. 매핑 JSON으로 기업 컬럼과 표준 컬럼을 연결하고, 변환 뒤 동일한 검증 파이프라인을 재사용하도록 했습니다.

---

### 3.3 `src/enterprise_data_validator.py` — 불량 데이터 차단기

**역할**

- 파일 존재 여부, 문자 인코딩, 필수 컬럼, 데이터 형식을 검사합니다.
- 중복 LOT·VIN·클레임 키를 차단합니다.
- 존재하지 않는 LOT이나 VIN을 참조하는 데이터를 차단합니다.
- 오류가 있으면 `READY`가 아닌 `BLOCKED` 결과를 반환합니다.

**핵심 함수**

- `read_csv_safely()`：안전한 CSV 읽기
- `validate_value()`：날짜·정수·비율 등 값 검증
- `validate_file()`：파일 단위 검사
- `validate_relationships()`：LOT–검사–VIN–클레임 참조관계 검사
- `validate_directory()`：전체 입력 검증

**왜 중요한가**

위험 계산식보다 먼저 데이터 품질이 확보되어야 합니다. 잘못된 데이터로 계산한 정확한 공식은 정확한 결과가 아닙니다.

**면접 답변**

> 형식 오류만 보는 것이 아니라 검사 데이터의 LOT이 실제 LOT 테이블에 존재하는지, 보증수리 VIN이 차량 데이터에 존재하는지까지 참조무결성을 검사합니다.

### 3.4 `src/enterprise_risk_analyzer.py` — 위험과 손익 계산기

**역할**

- 공정 편차, 재검률, 보증수리 신호, 부품 안전등급을 조합합니다.
- LOT별 위험점수를 `HIGH`, `WATCH`, `NORMAL`로 구분합니다.
- 해당 LOT이 장착된 VIN을 영향 차량으로 연결합니다.
- 안전·동력·편의·소프트웨어 부품에 따라 대응방법을 다르게 제시합니다.
- 예방 차량, 회피손실, 조기조치비, 순편익, ROI를 계산합니다.

**핵심 함수**

- `risk_score()`：위험점수와 이유 생성
- `action_for()`：부품 종류와 출고 상태에 맞는 대응 결정
- `analyze()`：전체 LOT 분석과 결과 파일 생성

**현재 위험규칙**

```text
공정편차 3σ 이상          +30점
공정편차 2σ 이상          +20점
재검률 10% 이상           +25점
재검률 7% 이상            +15점
보증수리 3건 이상         +25점
기준보다 높은 수리율      +20점
안전 핵심부품 가중치      +20점
주행 영향부품 가중치      +10점

HIGH  : 55점 이상
WATCH : 25점 이상
```

**경제성 공식**

```text
예방 차량 = 영향 차량 × 조기대응 성공률
회피손실 = 예방 차량 × (현장수리비 + 고객보상비)
조기조치비 = 예방 차량 × 출고 전 조치비
순편익 = 회피손실 - 조기조치비 - 고정 프로그램 비용
ROI = 순편익 ÷ 총비용
```

**반드시 덧붙일 말**

현재 성공률과 비용은 기업 실측값이 아니라 시뮬레이션 가정입니다. 실제 기업 데이터로 교체하고 재승인해야 합니다.

### 3.5 `src/enterprise_database.py` — 결과 보관·검색 계층

**역할**

- 표준 데이터와 분석 결과를 SQLite 데모 DB에 적재합니다.
- 임시 `.building` DB를 만든 뒤 무결성 검사를 통과해야 원본을 교체합니다.
- 파일별 SHA-256을 저장해 입력 파일 추적성을 남깁니다.
- LOT, VIN, 협력사, 부품번호, 위험등급으로 검색합니다.

**핵심 함수**

- `_create_schema()`：데모 DB 테이블과 인덱스 생성
- `build_database()`：검증·임시적재·무결성 검사·교체
- `search_database()`：조건 기반 검색

**보안상 중요한 코드**

```python
connection.execute(sql, params)
```

검색값을 SQL 문자열에 직접 붙이지 않고 파라미터로 전달하여 SQL Injection 위험을 줄입니다.

**PostgreSQL과 SQLite의 차이**

- SQLite：로컬 데모와 빠른 자동검사
- PostgreSQL：기업형 관계구조, 대량 데이터, 동시조회, 트랜잭션 시험

**면접 답변**

> 로컬 실행은 설치 부담이 적은 SQLite를 사용하고, 기업 적용 구조와 성능 검증은 PostgreSQL로 분리했습니다. 두 DB의 목적이 다릅니다.

### 3.6 `src/enterprise_dashboard.py` — 화면과 API 서버

**역할**

- 대시보드 HTML을 제공합니다.
- 요약, LOT·VIN 검색, 모델검증, 관리자 계정, 감사기록 API를 제공합니다.
- 데이터 반입 전 매핑 미리보기와 승인 기능을 제공합니다.
- 요청 크기와 입력값을 제한하고 공통 보안 헤더를 응답에 넣습니다.

**주요 API**

|---|---|---|
| `/api/summary` | 대시보드 요약 | VIEW_DASHBOARD |
| `/api/search` | LOT·VIN 검색 | SEARCH |
| `/api/model-validation` | 모델 검증 결과 | VIEW_DASHBOARD |

**면접 답변**

### 3.7 `src/enterprise_security.py` — 인증·권한·감사기록

**역할**

- 관리자, 품질담당자, 조회자의 권한을 분리합니다.
- 비밀번호를 PBKDF2-SHA256으로 반복 해시합니다.
- 로그인 세션과 CSRF 토큰을 발급합니다.
- 5회 로그인 실패 시 15분 잠금 처리합니다.
- 로그인·검색·계정 변경 기록을 감사 테이블에 남깁니다.
- 사용자와 접속주소는 감사 조회 시 HMAC 기반 참조값으로 가명처리합니다.
- 감사기록은 PoC 기준 90일 이후 삭제합니다.

**역할별 권한**

| 역할 | 권한 |
|---|---|
| ADMIN | 화면·검색·반입 미리보기·반입 승인·계정관리·감사조회 |
| QUALITY | 화면·검색·반입 미리보기 |
| VIEWER | 화면·검색 |

**중요한 한계**

PoC 보안이 기업 운영 보안의 완료를 뜻하지 않습니다. 운영 시에는 SSO, MFA, TLS, KMS/Secret Manager, 망 분리, 보안관제, 백업복구와 회사 보안정책 연동이 추가로 필요합니다.

**역할**

- 합성 LOT으로 고정 경보규칙을 시험합니다.
- 비용과 성공률 분포를 이용해 경제성 시뮬레이션을 실행합니다.
- 검증 결과를 JSON과 보고서용 파일로 출력합니다.

**핵심 함수**

- `public_backtest()`：공개데이터 선행신호 확인
- `synthetic_lot_test()`：합성 LOT 경보규칙 시험
- `economic_simulation()`：확률분포 기반 ROI 범위 계산
- `verify()`：재현성·기준 통과 검사

**구분해서 설명할 것**

- 공개 백테스트 결과：공개 신호의 선행 가능성
- 합성 LOT 결과：기능과 규칙 작동 여부
- 경제성 시뮬레이션：가정 조건에서의 손익 범위
- 기업 실증：아직 수행하지 않은 실제 성능 확인 단계

## 4. PostgreSQL 구조를 설명하는 방법

PostgreSQL 스키마에는 12개 업무 테이블이 있으며 네 묶음으로 설명하면 쉽습니다.

### 원천 기준정보

- `supplier`：협력사
- `part`：부품과 안전등급
- `process`：공정·공장·라인
- `vehicle`：가명 차량키와 생산정보
- `data_load_batch`：데이터 반입 이력

### 생산·현장 데이터

- `part_lot`：입고된 부품 LOT
- `process_inspection`：공정검사값과 재검률
- `vehicle_part_installation`：어떤 LOT이 어떤 차량에 장착됐는지 연결
- `warranty_claim`：보증수리·고장 정보

### 판단 데이터

- `cost_policy`：조기조치·현장수리·고객보상 비용 기준
- `risk_assessment`：LOT 위험점수·권고조치·예상 손익
- `affected_vehicle`：위험 LOT이 장착된 영향 차량

### 핵심 관계

```text
supplier → part_lot ← process_inspection
                    ↓
vehicle ← vehicle_part_installation
   ↓
warranty_claim

part_lot → risk_assessment → affected_vehicle
```

## 5. 테스트 코드를 설명하는 방법

실제 `unittest` 재실행 결과 **26개 테스트가 모두 통과**했습니다.

### 테스트가 확인하는 것

- 잘못된 비율값을 0으로 바꾸지 않고 차단
- 필수 파일 누락 차단
- 존재하지 않는 VIN 참조 차단
- 기업 한글 컬럼 매핑
- 데이터 오류 시 뒤 단계 중단
- 실패 실행이 기존 정상 DB를 덮지 않음
- SQL Injection 형태 입력의 파라미터 처리
- LOT·VIN 검색
- 위험 LOT과 영향 VIN 생성
- 관리자 초기 로그인과 역할별 권한
- 로그인 실패 감사기록
- 계정 비활성화
- 대량 시험용 데이터 생성

### 면접 답변

> AI가 생성한 코드라고 해서 그대로 신뢰하지 않았습니다. 정상 흐름뿐 아니라 잘못된 입력, 참조오류, SQL Injection 입력, 로그인 실패, 계정 권한과 롤백을 자동검사했고 현재 26개가 통과합니다.

## 6. 자주 나오는 코드 질문 12개

### Q1. 메인 진입점은 어디입니까?

기업 데이터 전체 흐름은 `enterprise_pipeline.py`의 `run_pipeline()`입니다. 공개 백테스트와 경제성 시뮬레이션은 `run_project.py`의 `main()`에서 실행됩니다.

### Q2. 기업 데이터가 들어오면 가장 먼저 무엇을 합니까?

`enterprise_import.py`에서 기업 컬럼을 표준 컬럼으로 변환하고, 즉시 `enterprise_data_validator.py`의 검증을 실행합니다.

### Q3. 위험점수는 머신러닝입니까?

현재 기업 PoC의 핵심 위험점수는 설명 가능한 고정 규칙입니다. 내부 데이터와 라벨이 확보되기 전 복잡한 ML 성능을 과장하지 않기 위한 선택입니다.

### Q4. 리콜 여부를 코드가 자동 결정합니까?

아닙니다. 코드는 위험등급과 권고조치를 제시합니다. 실제 출고보류나 리콜은 품질·안전 책임자의 승인 대상입니다.

### Q5. 왜 VIN 대신 vehicle_key도 사용합니까?

기업 스키마에서는 실제 VIN을 최소화하고 가명 차량키를 사용할 수 있도록 설계했습니다. 업무상 실제 VIN이 필요한 사용자만 제한적으로 연결해야 합니다.

### Q6. 오류가 난 데이터는 어디로 갑니까?

운영 DB에 바로 넣지 않습니다. 실행별 폴더와 staging 영역에 분리하고, 검증 실패 시 `BLOCKED`로 종료합니다.

### Q7. DB가 중간에 깨질 수 있지 않습니까?

SQLite 데모는 `.building` 임시 DB에 모두 적재하고 무결성 검사를 통과한 뒤 `os.replace()`로 교체합니다. PostgreSQL 시험에서는 트랜잭션 롤백을 검증했습니다.

### Q8. SQL Injection은 어떻게 막습니까?

검색조건을 SQL 문자열에 직접 합치지 않고 `?` 플레이스홀더와 별도 파라미터 목록으로 전달합니다.

### Q9. 세션 쿠키는 어떻게 보호합니까?

`HttpOnly`, `SameSite=Strict`, 8시간 만료를 사용합니다. 실제 HTTPS 배포에서는 `Secure` 속성과 기업 SSO가 추가로 필요합니다.

### Q10. 관리자와 품질담당자의 차이는 무엇입니까?

관리자만 계정 발급·활성화·감사기록 조회·반입 승인을 할 수 있고, 품질담당자는 대시보드·검색·반입 미리보기까지만 가능합니다.

### Q11. 실제 기업 적용 시 가장 먼저 바꿀 파일은 무엇입니까?

기업 컬럼 매핑 JSON, `enterprise_analysis_rules.json`의 표본 기준·비용·성공률, 인증·비밀정보 환경설정을 해당 기업 기준으로 교체해야 합니다.

### Q12. 지금 가장 큰 기술적 한계는 무엇입니까?

실제 기업 데이터로 탐지율·정밀도·오탐 비용·ROI를 검증하지 못했다는 점입니다. 운영 인프라 측면에서는 SSO, KMS, TLS, 망 분리, 보안관제와 백업복구 연동이 남아 있습니다.

## 7. 코드를 직접 열어 설명할 때의 순서

1. `enterprise_pipeline.py`를 열어 네 단계 흐름을 보여줍니다.
2. `enterprise_risk_analyzer.py`의 `risk_score()`에서 설명 가능한 규칙을 보여줍니다.
3. 같은 파일의 `action_for()`에서 안전·소프트웨어·편의 부품의 대응 차이를 보여줍니다.
4. `enterprise_database.py`의 임시 DB·무결성 검사·파라미터 검색을 보여줍니다.
5. `enterprise_security.py`의 `ROLE_PERMISSIONS`, 비밀번호 해시, 로그인 잠금을 보여줍니다.
6. `tests` 폴더에서 정상·실패·보안 시험이 분리돼 있음을 보여줍니다.

발표 중 코드를 너무 오래 보여주지 말고, 한 파일에서 한 가지 판단만 설명합니다.

## 8. AI 코딩 도구 사용에 대한 정확한 표현

### 좋은 답변

> 구현 과정에서 AI 코딩 도구의 도움을 받았습니다. 제가 직접 한 일은 현장 경험을 바탕으로 문제와 필요한 데이터 구조를 정의하고, 기능·보안·경제성 요구사항을 정한 뒤 실행 결과를 확인하고 반복 수정한 것입니다. 생성된 코드는 자동검사와 오류·롤백·동시조회 시험으로 검증했습니다.

### 피해야 할 답변

- “제가 모든 코드를 처음부터 직접 작성했습니다.”
- “AI가 만들어서 자세한 내용은 모릅니다.”
- “테스트가 통과했으니 기업에서 바로 쓸 수 있습니다.”

### 모르는 코드를 질문받았을 때

> 그 부분의 내부 구현을 정확히 외우고 있지는 않습니다. 다만 입력과 출력, 전체 흐름에서의 역할은 설명할 수 있습니다. 실제 수정 시에는 먼저 재현 테스트를 만들고 해당 함수와 호출부를 확인한 뒤 수정하겠습니다.

## 9. 마지막 요약

면접에서 보여줘야 할 것은 코드를 많이 외웠다는 사실이 아닙니다.

- 왜 이 데이터가 필요한지
- 어떤 오류를 먼저 차단하는지
- 위험 결과가 VIN과 손익으로 어떻게 연결되는지
- 자동 판단과 사람의 승인을 어떻게 구분했는지
- 공개·합성 결과와 기업 실증을 어떻게 구분했는지
- AI가 만든 결과를 어떤 시험으로 확인했는지

이 여섯 가지를 설명할 수 있으면 AutoQ-Guard의 핵심 구조를 이해하고 있다고 말할 수 있습니다.
